# JavaScript vs TypeScript: отличия и концепции применения

> Не «два языка», а язык и система типов поверх него.
> Разбор границ, компромиссов и практических критериев выбора.
> Актуально на **31 августа 2026** (TypeScript 7.0, Node.js с нативным стриппингом типов).

---

## 1. Главный тезис

**TypeScript — это не надстройка над JavaScript в смысле «JS + фичи».
Это статический анализатор с собственным языком аннотаций, который стирается перед выполнением.**

Из этого следует всё остальное:

- Ни одна строка типов не доживает до рантайма.
- Проверка типов и генерация кода — **два независимых процесса**. `tsc` выдаёт JS даже при ошибках типов (если не включён `noEmitOnError`).
- «Ошибка TypeScript» — это мнение анализатора, а не отказ движка. Программа может быть валидной и работать при красном компиляторе.
- Ни одна гарантия TS не переживает границу процесса: HTTP, файл, БД, `localStorage`, `process.env`.

Три слова, которые описывают систему целиком: **superset**, **erasure**, **structural**.

## 2. Три границы, которые объясняют почти всё

### 2.1 Superset — надмножество (почти)

Любой валидный `.js` — валидный `.ts`. Переименование файла не ломает код.
Это давало TypeScript главное конкурентное преимущество перед Dart, CoffeeScript и Flow:
**инкрементальная миграция без переписывания**.

Оговорки, где надмножество протекает:

- При `strict` (а с TS 6.0 это дефолт) валидный JS выдаст сотни ошибок — синтаксически он всё ещё TS, но не компилируется чисто.
- Некоторые старые конструкции JS запрещены в TS-модулях: `with`.
- Обратное неверно: `.ts` — **не** валидный JS.

### 2.2 Type erasure — стирание типов

Компиляция TS = удаление аннотаций + (опционально) даунлевелинг синтаксиса.

```ts
function greet(name: string): string { return `Hi, ${name}`; }
```
↓
```js
function greet(name) { return `Hi, ${name}`; }
```

**Следствие №1:** нулевая цена в рантайме. Никакой проверки, никакого метаданных-слоя, никакого влияния на производительность.

**Следствие №2:** невозможна ни одна операция, требующая типа в рантайме.
Нет `typeof MyInterface`, нет рефлексии по типам, нет `instanceof` для интерфейса,
нет перегрузки по типам аргументов.

**Следствие №3:** это ровно то, что позволило Node.js, Deno и Bun выполнять `.ts` напрямую —
им достаточно вырезать аннотации, а не понимать их.

### 2.3 Structural typing — структурная типизация

TS сравнивает типы **по форме**, а не по имени объявления (в отличие от Java, C#, C++).

```ts
interface Point { x: number; y: number }
class Vec { constructor(public x: number, public y: number) {} }

const p: Point = new Vec(1, 2);   // OK — форма совпала, родство не требуется
```

Это следствие природы JS: объектные литералы не имеют номинального «класса».
Плюс — работает с любым чужим кодом без адаптеров. Минус — типы взаимозаменяемы,
когда логически не должны быть:

```ts
type UserId = string;
type OrderId = string;
declare function cancel(id: OrderId): void;
const uid: UserId = "u_1";
cancel(uid);   // компилируется. И это баг.
```

Лечится **branded types** — искусственным номинальным маркером (см. §9).

## 3. Что именно TypeScript добавляет

Категории, а не список синтаксиса.

| Категория | Инструменты | Зачем |
|---|---|---|
| **Аннотации** | `x: T`, возвращаемые типы, параметры | Базовый уровень контракта |
| **Именование форм** | `interface`, `type`, `enum` | Переиспользуемые описания |
| **Композиция** | union `A \| B`, intersection `A & B`, литеральные типы `"a" \| "b"` | Моделирование состояний, а не структур |
| **Параметризация** | generics, constraints `extends`, `const` type params, вариантность | Обобщённые контейнеры и функции |
| **Сужение** | narrowing, type guards, `is`, `asserts`, discriminated unions, exhaustiveness через `never` | Компилятор понимает поток управления |
| **Вычисления над типами** | conditional types, `infer`, mapped types, template literal types, `keyof`/`typeof`/индексный доступ | Типы, выводимые из других типов |
| **Люки** | `any`, `unknown`, `as`, `!`, `@ts-ignore`, `@ts-expect-error` | Явные точки отказа от гарантий |
| **Эргономика** | `satisfies`, `readonly`, `as const`, optional `?`, перегрузки сигнатур | Точность без потери вывода |
| **Модульность типов** | `.d.ts`, `declare`, `import type`, module augmentation, DefinitelyTyped | Типизация чужого кода |

### Ключевое различие в мышлении

В JS вы описываете **данные и действия**. В TS вы дополнительно описываете
**множество допустимых значений**. Union-типы — не «или то, или это», а буквально
операция объединения множеств; `never` — пустое множество; `unknown` — универсум.
Половина «магии» TS становится очевидной, если читать типы как множества.

```ts
type State =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "done"; data: string }
  | { status: "error"; error: Error };

function render(s: State) {
  switch (s.status) {
    case "idle":    return "—";
    case "loading": return "…";
    case "done":    return s.data;          // сузилось, data доступна
    case "error":   return s.error.message;
    default: {
      const _exhaustive: never = s;          // забыли ветку → ошибка компиляции
      return _exhaustive;
    }
  }
}
```

Это то, ради чего берут TS. Не `x: number`, а **невозможность собрать проект,
забыв обработать состояние**.

## 4. Система типов: свойства, которые нужно знать

### Она Тьюринг-полная

Conditional + mapped + recursive types делают систему типов полноценным языком вычислений.
Отсюда и мощь (`Prettify<T>`, роутеры с типизацией из строки пути), и проблема:
компилятор можно уронить в экспоненту. `tsc --diagnostics` и `--generateTrace` существуют не случайно.

### Она намеренно unsound

**Soundness** = система типов никогда не пропускает ошибку типов.
TypeScript официально отказался от этой цели. Из
[TypeScript Design Goals](https://github.com/microsoft/TypeScript/wiki/TypeScript-Design-Goals),
раздел Non-goals:

> «Apply a sound or "provably correct" type system. Instead, strike a balance between
> correctness and productivity.»

Известные дыры, которые останутся навсегда:

| Дыра | Пример | Почему оставлена |
|---|---|---|
| **Ковариантность массивов** | `const a: Animal[] = dogs; a.push(cat)` | Иначе большая часть реального кода не типизируется |
| **Бивариантность параметров методов** | Обработчики событий, DOM API | Совместимость с существующими библиотеками |
| **`any`** | Заражает всё, к чему прикоснётся | Необходим для миграции |
| **Type assertions `as`** | `{} as User` — ложь компилятору | Escape hatch для случаев, где вы правы, а вывод нет |
| **Index signatures** | `obj[k]` даёт `T`, а не `T \| undefined` без `noUncheckedIndexedAccess` | Эргономика по умолчанию |
| **`.d.ts` могут врать** | Типы пакета не соответствуют его коду | Типы пишут люди, часто не авторы |
| **Границы I/O** | `JSON.parse` возвращает `any` | Проверить нечем — данных ещё нет |

**Практический вывод:** TS сокращает класс ошибок, но не даёт доказательства.
Кто хочет soundness — смотрит в сторону ReScript, Elm, PureScript. Кто хочет
работать с экосистемой npm — берёт TS и знает про дыры.

### Она gradual

`any` и `unknown` — два способа сказать «здесь я не знаю тип», с противоположной семантикой:

```ts
let a: any;      a.foo.bar();      // разрешено всё. Тишина.
let u: unknown;  u.foo;            // ошибка. Сначала сузь.
```

Правило: **`unknown` на входе, `any` — никогда**, кроме точечных мест с комментарием-обоснованием.
`any` — это не «неизвестный тип», это «выключить проверку в этой точке и во всём, что от неё зависит».

## 5. Где TypeScript не работает — границы приложения

Это самая недооценённая тема при переходе с JS.

Типы описывают **внутреннюю** согласованность программы. На каждой границе,
где данные приходят извне, гарантия обрывается:

```ts
const user: User = await res.json();   // компилируется. Проверок ноль.
```

`res.json()` возвращает `Promise<any>`. Аннотация `: User` — это ваше обещание, а не факт.
Сервер поменял поле — TypeScript не заметит ни на компиляции, ни в рантайме.

**Точки, где нужен рантайм-валидатор:**

- HTTP-ответы, WebSocket-сообщения, webhooks
- `JSON.parse`, `localStorage`, `sessionStorage`, IndexedDB
- `process.env` (всё — `string | undefined`, даже если вы объявили иначе)
- CLI-аргументы, конфиги (YAML/TOML/JSON)
- Данные из БД без генерации типов из схемы
- Сообщения между воркерами и iframe (`postMessage`)
- Любой `any` из нетипизированной зависимости

**Решение:** схема как единственный источник правды, тип выводится из неё.

```ts
import { z } from "zod";

const User = z.object({ id: z.string(), age: z.number().int().min(0) });
type User = z.infer<typeof User>;      // тип выведен из схемы, не наоборот

const user = User.parse(await res.json());  // и проверка, и тип
```

Альтернативы: **valibot** (меньше бандл), **arktype** (синтаксис ближе к TS),
**typia** (компиляция схемы из типа), **ajv** + JSON Schema (когда схема — контракт между сервисами).

Отдельная стратегия — **генерация типов из источника истины**, а не ручное описание:
OpenAPI → `openapi-typescript`, GraphQL → codegen, БД → Prisma / Drizzle / Kysely,
protobuf → `ts-proto`. Здесь TS работает в полную силу, потому что типы не расходятся с реальностью по построению.

## 6. Рантайм-фичи TypeScript — то, что ломает стирание

Не весь TS стирается. Есть небольшой набор конструкций, генерирующих код.
Это исторический долг: они появились до того, как политика «типы стираются» стала строгой.

| Конструкция | Что генерирует | Статус |
|---|---|---|
| `enum` | Объект с прямым и обратным мэппингом | Избегать. Брать `as const` объект или union литералов |
| `const enum` | Инлайн значений | Ломается при `isolatedModules`, несовместим с bundler'ами |
| `namespace` с кодом | IIFE | Мёртвая ветка, до ES-модулей |
| Parameter properties | Присваивания в конструкторе | Удобно, но не стирается |
| Legacy decorators (`experimentalDecorators`) | Вызовы `__decorate` | Ждать stage-4 версии из ES2027+ |

Флаг **`erasableSyntaxOnly`** (TS 5.8+) запрещает всё перечисленное на уровне компилятора.
Включайте его, если хотите, чтобы код запускался напрямую в Node/Deno/Bun без сборки.

```ts
// вместо enum
const Status = { Idle: "idle", Done: "done" } as const;
type Status = typeof Status[keyof typeof Status];   // "idle" | "done"
```

## 7. Экосистема на август 2026

### TypeScript 6.0 — 23 марта 2026

Последний релиз компилятора, написанного на JavaScript. Фактически — подготовка к 7.0:

- `strict: true` **по умолчанию**;
- `module` по умолчанию `esnext`, `target` — `es2025`;
- `types: []` по умолчанию — `@types`-пакеты надо объявлять явно;
- типы `Temporal`, `Map.getOrInsert`, `RegExp.escape`; поддержка target ES2025;
- флаг `--stableTypeOrdering` для диагностики расхождений с 7.0;
- депрекация: `moduleResolution node`, `baseUrl`, target ES5, AMD/UMD/SystemJS.

### TypeScript 7.0 — 8 июля 2026

Компилятор переписан на **Go**. Это самое большое событие в TS за десять лет.

- **8–12× быстрее** на полных сборках. VS Code: 125,7 с → 10,6 с. Slack: CI type-check 7,5 мин → 1,25 мин.
- Память: −6…−26 %.
- Многопоточность с разделяемой памятью; параллельные парсинг, проверка и эмит.
- Watcher переписан на Go-порт Parcel watcher.
- Удалено: target ES5, AMD/UMD/SystemJS, classic module resolution, `downlevelIteration`.
- Новые дефолты: `strict: true`, `module: esnext`, `types: []`, `rootDir: ./`.

⚠️ **Главное ограничение 7.0: нет публичного API.** Всё, что программно дёргает
компилятор — webpack-лоадеры, `typescript-eslint`, тулинг Vue и Angular — пока работает
только на 6.0. Microsoft выпустила пакет совместимости `@typescript/typescript6`,
чтобы 6.0 и 7.0 стояли рядом. API обещан в 7.1.

**Практический вывод на сегодня:** ставить 7.0 как type-checker в CI можно и нужно
(ради скорости), но выкидывать 6.0 из проекта рано.

### Нативный TypeScript в рантаймах

| Рантайм | Как |
|---|---|
| **Node.js** | Стриппинг типов **стабилен** (v24.12 / v25.2), включён по умолчанию с v22.18/v23.6, в v26 экспериментальный флаг убран. `tsconfig.json` **игнорируется**, проверки типов нет, path-алиасы не работают. Не поддерживаются `enum`, `namespace` с кодом, parameter properties, декораторы. Type-only импорты обязаны быть помечены `import type` |
| **Deno** | TS первого класса с самого начала, с проверкой типов |
| **Bun** | Выполняет TS напрямую, транспилятор встроен, проверки типов нет |
| **Браузеры** | Ничего. Только сборка |

Рекомендуемый `tsconfig.json` для нативного запуска в Node:

```json
{
  "compilerOptions": {
    "noEmit": true,
    "target": "esnext",
    "module": "nodenext",
    "rewriteRelativeImportExtensions": true,
    "erasableSyntaxOnly": true,
    "verbatimModuleSyntax": true
  }
}
```

Модель, к которой пришла индустрия: **рантайм выполняет, `tsc` проверяет.**
Две независимые операции, не одна.

### Типы в самом стандарте?

Предложение **TC39 Type Annotations** («Types as Comments») — сделать так, чтобы движки
игнорировали аннотации, как комментарии. С 2022 года стоит на **stage 1**, репозиторий
не обновляется с 2023-го. Реально проблему решили рантаймы, а не комитет.
Рассчитывать на это в обозримом будущем не стоит.

## 8. Концепции применения: когда что

### Три режима, а не два

Между «чистый JS» и «полный TS» есть третий режим, о котором часто забывают:
**JSDoc-типы в `.js` файлах**.

```js
// @ts-check
/** @param {string} name @returns {string} */
function greet(name) { return `Hi, ${name}`; }
```

С `checkJs: true` вы получаете почти всю систему типов TS без шага сборки и без
`.ts`-файлов. Так типизирован сам Node.js, так долго жил Svelte, так удобно
типизировать конфиги и скрипты. Ограничение: синтаксис громоздкий,
сложные типы читаются плохо.

### Матрица выбора

| Ситуация | Рекомендация |
|---|---|
| Одноразовый скрипт, glue-код, `<script>` в HTML | **JS**. Цена настройки больше пользы |
| Прототип, который проживёт неделю | **JS** или JS + `// @ts-check` |
| Библиотека на npm | **TS обязательно**. Типы — часть публичного API. Без `.d.ts` вас не возьмут |
| Приложение, срок жизни > 6 месяцев | **TS** |
| Команда больше 2 человек | **TS**. Типы — это машиночитаемая документация контрактов |
| Домен со сложными состояниями (заказы, платежи, workflow) | **TS**, ради discriminated unions и exhaustiveness |
| Легаси-JS, который надо не сломать | **JS + JSDoc + `checkJs`**, потом постепенная миграция |
| Обучение программированию с нуля | **JS**. Типы — второй слой абстракции, он мешает на старте |
| Конфиги, build-скрипты | **JS + `@ts-check`** — не нужен шаг сборки |
| Скорость итерации критичнее корректности (хакатон, MVP на выброс) | **JS** |

### Что TS даёт помимо ловли ошибок

Часто это ценнее самой проверки типов:

1. **IDE**. Автодополнение, переход к определению, поиск использований, автоимпорты.
   На большой кодовой базе выигрыш измеряется часами в день.
2. **Рефакторинг**. Переименование поля через 200 файлов — механическая операция, а не аудит.
3. **Документация, которая не устаревает**. Сигнатура не может разойтись с кодом.
4. **Дизайн API**. Попытка типизировать функцию часто вскрывает, что она делает три разных вещи.
5. **Онбординг**. Новый человек читает типы вместо того, чтобы запускать код и смотреть, что придёт.

### Цена

Честный список того, что вы платите:

- Шаг сборки или отдельный процесс проверки (частично снят нативными рантаймами).
- Время `tsc` в CI (радикально снижено в 7.0).
- Кривая обучения: generics, вариантность, conditional types — это отдельный язык.
- Риск over-engineering: типы ради типов, четырёхэтажные `infer`, нечитаемые утилиты.
- Зависимость от качества чужих `.d.ts`.
- Трение с быстро меняющимися требованиями: рефакторинг типов идёт до рефакторинга кода.

## 9. Практические паттерны

### `satisfies` вместо аннотации

```ts
// аннотация расширяет тип — теряется точность
const routes: Record<string, string> = { home: "/", about: "/about" };
routes.home;   // string

// satisfies проверяет, но сохраняет вывод
const routes2 = { home: "/", about: "/about" } satisfies Record<string, string>;
routes2.home;  // "/"  — литеральный тип сохранён
```

### Branded types против структурной подмены

```ts
declare const brand: unique symbol;
type Brand<T, B> = T & { readonly [brand]: B };

type UserId  = Brand<string, "UserId">;
type OrderId = Brand<string, "OrderId">;

const asUserId = (s: string) => s as UserId;

declare function cancel(id: OrderId): void;
cancel(asUserId("u_1"));   // ошибка компиляции. Теперь правильно
```

### `unknown` на границе, сужение внутрь

```ts
function handle(raw: unknown) {
  if (typeof raw !== "object" || raw === null) throw new TypeError();
  // дальше — валидатор, а не as
}
```

### Строгие флаги по возрастанию боли

Порядок включения при миграции легаси:

1. `strict: true` (в TS 6.0+ уже дефолт) — это уже 8 флагов сразу
2. `noUncheckedIndexedAccess` — `arr[i]` становится `T | undefined`. Больно и правильно
3. `exactOptionalPropertyTypes` — `{a?: string}` перестаёт принимать `{a: undefined}`
4. `noImplicitOverride`, `noPropertyAccessFromIndexSignature`
5. `erasableSyntaxOnly` — если нужен нативный запуск
6. `verbatimModuleSyntax` — предсказуемый эмит импортов

### Стратегия миграции JS → TS

1. Включить `allowJs` + `checkJs` + `// @ts-nocheck` в самых грязных файлах.
2. Переименовать листовые модули (утилиты без зависимостей) в `.ts`.
3. Типизировать **границы** — API-клиенты, парсеры, конфиг. Именно там ловится больше всего.
4. Двигаться от листьев к корню, не наоборот.
5. `any` разрешён, но с `// TODO(types):` и счётчиком в CI, который не должен расти.
6. `strict` включать **сразу**, а не «потом» — иначе типы приедут неправильные и их придётся переделывать.

### Антипаттерны

- `as` вместо валидации на границе — типизированная ложь.
- `any` в сигнатуре публичной функции — заражение всей цепочки вызовов.
- `enum` в новом коде — не стирается, ломает нативный запуск.
- Интерфейс на каждый объект — избыточно, вывод типов справляется сам.
- Дублирование типов и Zod-схем вручную вместо `z.infer`.
- Типовая акробатика ради красоты — читать будет другой человек.
- `@ts-ignore` вместо `@ts-expect-error` — первый молча протухает, второй сам сообщит, когда ошибка исчезнет.

## 10. Сводка

| Ось | JavaScript | TypeScript |
|---|---|---|
| Что это | Язык, исполняется движком | Система типов + компилятор, стирается перед исполнением |
| Стандарт | ECMA-262, TC39, консенсус | Microsoft, без формального комитета |
| Проверка типов | В рантайме, при операции | На этапе компиляции, до запуска |
| Типизация | Динамическая, слабая | Статическая, структурная, gradual, unsound |
| Цена в рантайме | — | Ноль (кроме `enum` / `namespace` / декораторов) |
| Ошибки видны | При выполнении ветки | При написании кода |
| Шаг сборки | Не нужен | Нужен `tsc` или нативный стриппинг + отдельная проверка |
| Границы I/O | Не покрыты | **Тоже не покрыты** — нужен рантайм-валидатор |
| Порог входа | Низкий | Средний; generics и conditional types — высокий |
| Где выигрывает | Скрипты, прототипы, обучение, мелкий glue | Библиотеки, долгоживущие приложения, команды, сложные домены |
| Актуальная версия | ES2026 (17-е издание, июнь 2026) | TypeScript 7.0 (июль 2026, компилятор на Go) |

**Одной фразой:** JavaScript отвечает на вопрос «что произойдёт»,
TypeScript — на вопрос «что вообще может произойти». Второй вопрос имеет смысл
задавать, когда код живёт дольше, чем помнит его автор.
